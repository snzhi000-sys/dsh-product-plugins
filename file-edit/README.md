# dsh-file-edit

English | [中文](README.zh.md)

> All code in this project is generated by DeepSeek-V4-Pro and DeepSeek-V4-Flash.

> **About this copy**: this copy is vendored from the legacy unified project `harness-macos-desktop-plugin-suite/plugins/file-edit@1.13.43-local`, and is assembled in the new project as the product plugin `dsh-file-edit` with its built-in permission gates disabled wholesale. It only records changes for review and never vetoes or blocks any tool execution: the host registers no `tools.guard` and always allows `tools/pre-execute`; foreground bash/shell in a writable workspace is captured by "pre-execution snapshot + recursive watching" (`auditCoverage.kind: partial`). Boundaries: background Shell is allowed but not captured; writes outside the workspace snapshot scope and concurrent external changes may go unrecorded; the new kernel has no `shellTransactionLifecycle` concept, so the APFS COW transaction path is no longer used; the `shell_readonly` tool keeps its own read-only precondition check. The permission and Shell items below are updated to this semantics.

The DSH WebUI workspace file plugin, with two core capabilities:

1. **Workspace file browsing and editing**: file-tree browsing, multi-tab opening, syntax highlighting, Markdown rendering, and direct editing of file contents in the browser;
2. **Diff view**: line-level diffs for changed files, with per-block or whole-file accept/reject and undo after a rejection.

## Features

Opening a file in a cold session reads only the host-mounted session header or the persisted session header, without waiting for the whole conversation history and every pending file to hydrate. The cwd passed by the client is not an authorization basis; a session that does not exist is still refused. Read errors are not disguised as binary downloads, and a late open response does not switch back to the old session after a session switch.

When a file is opened, re-opened, or switched, the tab bar scrolls horizontally with a 180–250 ms deceleration animation until the current tab is just visible; a fully visible tab does not move, and an over-wide tab aligns to its start. Rapid switching retargets from the current position to the newest tab, and manual scrolling, touch, keys, or dragging abort the animation. Restoring the file view for the first time, switching sessions, and the system "reduce motion" setting position the tab directly. It moves neither the body text nor focus, and does not keep pulling the user's scroll position back because of review polling, typing, or drag reordering.

- The file tab row offers only file tabs and a "more" menu; the action area uses its own class names, so the legacy Message Edit message-action scanner does not insert "edit message" and "retry this turn".

- **Permission ownership**: AI calls to `file_delete` / `file_move` are no longer gated by this plugin reading the sandbox policy, and no longer refuse `read-only` or out-of-workspace targets at the tool entry or before a disk modification; sandbox, approval, and permission belong to the kernel, and this plugin only records changes. Whole-file and per-line saves from the file view remain confined to the current workspace and keep version checks and pending-review protection.

- **Workspace sidebar** (replaces the native browser): the project folder expands in two levels — session history (open a session / new session; ordered by most recent activity, each row showing a relative time label such as "2 min / 1 hr / 1 day") and the project file tree (double-click/single-click to open, manual ⟳ refresh, automatic refresh when the file set changes).
- **File browser host**: in a runtime where the official right sidebar is available, the browser is a page-type tab in the right sidebar — one tab carries the whole browser, and its inner document sub-tabs switch inside that tab; the entry is produced only by clicking a file in Explorer (the tab closes itself when there is no browsable document), and the session tab strip no longer carries a permanent "Files". Older products without this sidebar service still mount the browser in the session view, side by side with "Chat / Trace".
- **Top-bar "Files" tab**: the content area is a browser-style tab strip (switch / ✕ close / ✕ all / drag reorder / ● modified mark). The unified open entry also accepts plain text files outside the workspace: the Host replaces the normalized absolute path with an opaque ID, and the file is browsed read-only, with no whole-file or per-line editing.
- **Single file title**: the file name appears only in the browser-style file tab; the content toolbar does not repeat the title, and status labels such as Markdown / editing / modified start from the left.
- **Single-editor reference chips**: references are drawn by the Harness occurrence/backdrop, and input always stays with the native textarea, so Shift+Enter, IME composition, deletion, undo, and long-text scrolling do not switch implementation because a reference exists.
- **Rendered-view line references**: selecting text in the Markdown rendered view (or pressing Command+U) yields a true line-number reference `path:startLine-endLine` through the plugin's own ref codec. On send it serializes into an official `@path` mention plus line-range text (`@draft.md 第12-19行`), so the transcript folds it into an official file chip with a short label beside it instead of the raw marker; **the text of the selected lines is not sent**, and the model reads the file by range itself. Line numbers are annotated by the renderer itself: a block token's `map` gives the block's first line, and inline child tokens of a multi-line paragraph are split by `softbreak` along source lines, so every text fragment lands on an exact line; fenced code blocks are annotated line by line, and table cells belong to their row. When a selection endpoint lands on an element (triple-click, drag to the end of a block), it takes the first/last annotation inside that element instead of degrading to the block's start line. Known boundary: inline code that spans lines is folded into a space by markdown-it, and later text in the same paragraph lands on the start line of that code span (the drift stays inside the block, and the next block-level label re-anchors).
- **Division of labour between the two reference paths**: the diff view and code browsing (including their Command+U) use the official `@path` mention, with the line range appearing only in the chip's display name while the model receives the path alone; rendered-view line references likewise land in the message as an official mention, but write the line range into the text, because "the model knows which lines I referenced" is the purpose of a rendered-view reference. The input chips in both places declare the official `appearance`, so both draw the official file icon.
- **Modified file list** (above the input box): modifications/additions/deletions produced during the session by the agent file tools (write/edit/file_delete/file_move), with +/− stats, per-file accept/reject, accept all/reject all, and undo last rejection; the chat page and the file page both cap the panel height, scrolling the content area when there are many files while keeping the header collapse and the batch actions available. A structured `file_delete` handles files and directories inside and outside the workspace, and must move them completely into the persistent quarantine before deletion; every regular file in a directory enters the review ledger of the same deletion batch.
- **Review bar width**: the same width as the official input card — both are children of `.composerStack`, and the official card sits in a 16px side-margin container with `width:100%`, so the review bar takes `min(container width − 2×side-clearance, card-max-width)` and expresses its overlay stance with the same left and right insets. When a narrower width can no longer hold the address, it drops the inline original address first (the full path stays on the row's `title`), and the file name keeps its ellipsis.
- **Review bar ink**: follows the tiers of the official dock card and the official file tree — decorative glyphs all use the weakest `label-tertiary` (leading pencil, collapse arrow, file icon), only the title and the file name stay in `label-primary`, and the address line stays in `label-tertiary`; icon buttons step up one tier to `label-secondary` on hover, and accept/reject keep the `state-success`/`state-error` semantic colors, with one deliberate exception: the review green is the plugin's own `--dsh-fe-review-add` (`#19BB4D`) — the official success tier reads too dim on review copy — applied to the added-diff text and tint, the `+` stats, the "added" chip and the accept glyph, falling back to `state-success` when the variable is absent. All of these rules are scoped inside `.dsh-fe-bar`, so the file browser, which shares the same class names, is unaffected.
- **Icons come from the official set**: the review list, the file tree, deletion batches and file tabs all draw the same `FileTypeIcon` and folder icons the official file tree and Explorer use, resolved through the module table (`@deepseek-ai/dsh-client-ui-primitives`, declared in `dsh.client.inject`); the plugin keeps no hand-drawn generic file or folder glyph.
- **Opening a file at a target line**: clicking a row in the modified-file list opens that file at its first change; the plugin provides `dshFileEditOpen` (revision 1) as a Cordis service, so another package reads it with `ctx.get` and passes `line`/`endLine`, and the view scrolls that range into view and flashes it for 1.2s, while the edit view selects the range instead. The target is handed over once, so polling, editing and manual scrolling never pull the position back. The page global `window.__dshFileEdit` stays for one version as a fallback and publishes only `open`, the entry that has a consumer.
- **Batch closing of file tabs**: the tab bar uses a fixed three-dot "more file actions" entry whose menu offers "close all files" and "close processed files". The latter first refreshes the current session review state and closes only tabs that are already saved, have nothing pending review, and have no local unsaved draft; when the review refresh fails, no file is closed. The tab scroll area is separate from the action area, so the three-dot button and its menu stay visible when there are many files.
- **Inline Diff**: red/green line-level diff, 24-language syntax highlighting, block-level and file-level accept and reject, jump controls, read-only preview of large files, binary restore.
- **Baseline review**: whole-file accept = the current content becomes the new baseline; partial accept = only that hunk is settled into the baseline; partial reject = only that hunk is restored from disk to the baseline. After every partial operation the remaining diff is recomputed from the new `base → cur`, and no ordinal hunk ID is persisted, so when the agent modifies the same file again, already-reviewed content neither reappears nor wrongly hides other blocks. Whole-file reject writes the remaining baseline back to disk (rejecting an added file = deleting the file); a rejection is undoable (one level).
- **In-file editing**: direct editing in the file view (contentEditable), where user edits fold into the baseline and do not disturb the agent's pending hunks; an empty file accepts a first line directly.
- **Markdown rendered view**: `.md`/`.markdown` render directly when there is nothing pending review (GFM tables, fenced code highlighting, no line cap).
- **Event-driven review**: the complete before/after result of write/edit enters the current session ledger directly, including absolute-path text files outside the workspace; the mutating commands of the opt-in `str_replace_editor` tool (create/str_replace/insert) record the pre-image read before the call against the file after it; file_delete/file_move are likewise recorded at execution time. Review discovery does not depend on a workspace scan and is unaffected by the file tree's 8000-entry cap.
- **Subagent review attribution**: write/edit/file_delete/file_move and historical foreground Shell events in a session with `origin: subagent` are attributed along `parentSession` into the nearest visible parent session's review bar; ordinary child sessions such as message-edit forks keep independent ledgers and are not wrongly merged.
- **Out-of-workspace safe review**: external entries show the normalized absolute path and an "outside the workspace" mark, and accept/reject use only the Host-issued session ledger ID; they survive a restart, and a rejection verifies the on-disk version first, so it does not overwrite a newer modification produced by another session.
- **Transactional deletion quarantine**: `file_delete` first produces a directory manifest and a persistent `deletionBatchId`, uses an atomic move on the same volume, and across volumes copies in chunks with per-file SHA-256 verification before deleting the original path; a failed backup or verification forbids deletion. A top-level symlink, a filesystem root, the user home directory, the current workspace root, and the review state directory cannot be deletion targets, and a symlink inside a directory is backed up as the link itself without being followed. A rejected large deleted file is restored directly from quarantine, unrestricted by the ordinary text/binary snapshot size limits.
- **Deletion tombstone review**: a file created and then deleted in the same session no longer disappears as a net-zero change but is shown explicitly as "created then deleted in this session". The tombstone persists the deletion source, batch, time, and target; accept confirms that the file continues not to exist and ends the whole change, while reject only undoes the deletion, restores the quarantined content, and keeps the original addition pending review. The same holds for modify-then-delete: after rejecting the deletion, the earlier modification stays pending review.
- **Foreground Shell review**: foreground bash/shell/pwsh in a writable workspace uniformly goes through "pre-execution snapshot + recursive watching" capture, and after the command ends the additions, modifications, and deletions are settled against the workspace signature and candidate paths, reusing the existing ledger, quarantine, and restore. A failed snapshot or watch setup, a lost event, an out-of-scope write, a transient create-then-delete, and concurrent other processes may all go unrecorded or unattributed, but none of them blocks command execution any more. The session persistently keeps `auditCoverage.kind: partial` and claims no whole-disk recoverability. Shell entry points the ledger cannot capture are disclosed instead of denied: a background Shell call, and any call to an untracked compatibility Shell, are counted per session and named in the review bar's own uncaptured line, which is persisted with the session so the disclosure survives a restart.
- **Shell pre-modification snapshot transaction (disabled, no longer assembled)**: the new kernel has no `shellTransactionLifecycle`, so this transactional path is no longer used, foreground Shell is now captured by the "snapshot + watching" above, and `capturePartialShell` is likewise unused. The original design was: the Host fully enumerates the explicit writable roots; on macOS it performs one APFS recursive COW per root, falling back to a physical copy after checking whole-tree capacity and free space, with every payload still verified file by file through SHA-256. A compact manifest reuses the hashes of unchanged files from stable metadata such as mtime/ctime/size, and after the command ends it produces the complete added/modified/deleted change set; the watcher only supplies candidate path hints. Transactions of the same or mutually containing workspaces serialize until the persistent ledger commits, while disjoint workspaces run in parallel. Additions and modifications enter ordinary review, deletions move from the pre-command snapshot into the persistent quarantine, and the accept, reject, and whole-directory restore of `deletionBatchId` are reused. Running/captured transactions left behind by a Host crash continue to settle when the review bar is read again; expired prepared states and committed diagnostic snapshots are cleaned up lazily only during a later writable transaction or review recovery, and never enter the first-screen startup path.
- **Orthogonal external service capability**: the product Profile offers controlled capabilities through independent, structured Host tools; currently `dsh-lark-cli` exposes only selected Feishu commands. Ordinary document creation, update, import, and upload execute directly; high-risk operations such as deletion, rollback, sign-out, and removing access permission are approved one at a time. The subprocess may write only the lark-cli state directory and temporary directories, and cannot modify workspace files.
- **Directory deletion batch review**: a complete directory deletion aggregates into a single row in the existing review bar, showing the folder icon, path, red "delete" label, and batch actions in line with ordinary file rows; the expand arrow follows the directory path, and clicking the path or the arrow expands the files inside the directory. Expanded child files show only their relative path and do not repeat the "delete" or "created then deleted" state the parent already expresses. Accepting the whole deletion batch, or rejecting it and restoring the whole directory from quarantine — including empty directories and unfollowed symlinks — is supported. The top "accept all / reject all" also treats a complete directory as one batch and does not miss empty directories, symlinks, or the quarantine. Out-of-workspace batches still show "outside the workspace" and open with each file's original opaque ID. If a child file has already been reviewed on its own, the aggregate row automatically splits back into single files, and the batch interface refuses a partial restore.
- **Read-only browsing of external artifacts**: answer-footer artifacts, body-text file links, Explorer, and tool results share one unified open protocol. A plain file outside the workspace can be opened in "Files", but a directory is refused; a browsing ID cannot be used to save or to edit line by line. If that external file has been modified by the AI and entered the review ledger, the existing accept/reject flow still applies.
- **Immediate updates**: after the agent modifies, adds, deletes, or moves a file, the interface wakes immediately, with no need to wait for a whole-workspace scan or a manual refresh.
- **Snapshot-first startup recovery**: after a restart, the persisted pending-review ledger is shown immediately, and the on-disk calibration that targets only pending-review entries is then committed to a shared serial queue after the Harness first paint. That scheduling neither scans the workspace nor weakens review intensity; switching sessions cancels a calibration that has not started, and a late result from an already-started request is still refused by the session token.

## Assembly and enabling

This plugin is assembled by `distribution/profile-manifest.json`'s `productPlugins` (`dsh-file-edit` → `plugins/file-edit`) and loads with the App's Web Profile; it needs no separate install or update script. The host entry is `host/index.mjs`, and the client bundle the browser loads is `client/dist/client.js`.

## Runtime data

- Per-session review state (settled baseline, current disk snapshot, deletion batch associations, undo records) lives in `~/.dsh/dsh-file-edit-state/`, created and maintained by the plugin itself and restored automatically after a restart. v7 persists the ledger with atomic replacement and reads v2 through v6 compatibly; legacy positional hunk decisions still migrate by the v6 rules. The raw content and `manifest.json` of structured and Shell deletions live in `<sessionId>/quarantine/<deletionBatchId>/`, and unfinished Shell lifecycle evidence lives in `shell-transactions/`.
- When upgrading from the old name `dsh-files`, the host automatically migrates the old `~/.dsh/dsh-files-state/` on first start, so pending-review state is not lost.

## Known limitations

- Replaces the native WorkspaceBrowser: no search, no grouping/sorting menu, and no rename/delete/archive dialogs (adding a workspace and opening/creating a session are kept).
- Skipped directories: `.git` `node_modules` `.venv` `venv` `__pycache__` `.next` `.dsh` `.idea` `.vscode` `.cache` `.turbo` `.pytest_cache` `.mypy_cache` `.ruff_cache` `.eslintcache` `.DS_Store`; the tree caps at 8000 entries / 16 levels.
- Large files get no line-level diff: >512 KB or >8000 lines is marked `large` (text up to 512 KB can be previewed read-only for its first 4000 lines); a binary up to 4 MB can be restored by rejection.
- Foreground Shell is captured by "snapshot + watching" in every writable mode, executes within system permissions, and does not narrow writes through `audit_root`. An unavailable, over-limit, or failed snapshot or settlement neither blocks a command nor replays a command that already ran; the original success, non-zero exit, or exception is kept. The session persistently keeps `auditCoverage.kind: partial`, shows no generic review-incomplete copy or label, and appends no such notice to the Shell result. That record does not open an empty review bar on its own; actual operation errors and per-file restore limits are still preserved. Removing the notice does not mean whole-disk review is complete. Background Shell and persistent terminals are allowed but not captured, and their changes do not enter the review ledger; those calls, and any call to an untracked compatibility Shell (`powershell`, `shell_command`, `terminal_open`, `terminal_send`), are counted per session and named in the review bar's uncaptured line, so the list is never mistaken for complete evidence. The `str_replace_editor` mapping covers the commands the kernel tool defines; a preset that does not enable that tool produces no such calls.
- External service operations such as Feishu upload prefer the independent `lark_cli` tool, because it bypasses Shell and can write only the lark-cli state and temporary directories.
- A structured `file_delete` already covers transactional quarantine of files and directories, deletion tombstones, and aggregate review of directory batches. This plugin neither constrains the AI tools in the Harness tool pipeline nor replaces the user's own authority to operate files outside the App or in a system terminal.
- When `write` overwrites a file but the tool returns no pre-modification content, the row shows "pre-modification content unknown" and can only be accepted or handled manually; it is never misreported as an addition, and no data-destroying automatic rejection is offered.
- Settled baselines and pending-review state both persist across plugin restarts; if the disk keeps changing while closed, opening or reviewing still verifies the per-file version and requires a refresh.
